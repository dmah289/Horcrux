Tình huốngBus làm gì

Cách dùng

Khai báo event

LuậtLý do
readonly struct, implement IEventListener nhận một bản copy. Field mutable tạo ảo giác sửa được payload cho listener sau — thực tế không, và sai im lặng
Không dùng classConstraint chặn ở compile time; call site không thể new một event object mỗi lần bắn
Chịu được payload rỗngListener không chịu được null thì call site không publish rỗng event đó
 
public readonly struct PieceMatched : IEvent
{
    public readonly int Count;
    public PieceMatched(int count) => Count = count;
}

EventBus<PieceMatched>.Publish(new PieceMatched(3));

Nhu cầuCách làmGiữ handle?

Nghe một lần rồi thôiDispose handle ngay trong callbackCó

// Nghe suốt đời object
public sealed class ScoreLabel : MonoBehaviour
{
    private void Awake() => EventBus<PieceMatched>.Subscribe(OnMatched);
    private void OnMatched(PieceMatched e) { }
}

// Nghe theo bật/tắt
public sealed class ComboPopup : MonoBehaviour
{
    private Subscription<PieceMatched> subscription;
    private void OnEnable() => subscription = EventBus<PieceMatched>.Subscribe(OnMatched);
    private void OnDisable() => subscription.Dispose();
    private void OnMatched(PieceMatched e) { }
}

// Nghe một lần
public sealed class FirstMatchHint : MonoBehaviour
{
    private Subscription<PieceMatched> subscription;
    private void Awake() => subscription = EventBus<PieceMatched>.Subscribe(OnFirstMatch);
    private void OnFirstMatch(PieceMatched e) => subscription.Dispose();
}

Flow

Một lượt Publish: B huỷ D và đăng ký E giữa lượt
Publish(e) depth++ n = số ô lúc vào ô thêm giữa lượt nằm sau n ─► chờ Publish kế mỗi ô 0…n-1, theo thứ tự Subscribe: ô rỗng (đã Dispose) ─► bỏ qua owner UnityEngine.Object đã destroy ─► đánh dấu ô rỗng, bỏ qua còn lại ─► callback(e); exception ─► LogException, đi tiếp depth-- depth == 0 ─► dồn danh sách, bỏ ô rỗng

Lưu ý

ChỗSự thật
bẫyBẫy đáng nhớ nhấtSubscribe ở OnEnable mà quên Dispose ở OnDisable — object đang tắt vẫn nhận event, và lần bật lại bị chặn vì trùng đăng ký. Dòng LogError trong Editor là tín hiệu của đúng lỗi này; sửa call site, đừng tắt log.
bẫyTự rụng phủ đúng một cacallback.Target là UnityEngine.Object đã destroy. Disable, method static, object thường không rụng; lambda rụng hay không tuỳ cách compiler sinh code, nên coi mọi lambda là phải Dispose.
bẫyMain-thread onlyKhông lock: Publish hoặc Subscribe từ thread khác làm hỏng danh sách listener.
bẫyPublish lồng cùng kiểu cần điều kiện dừngThường không do ai cố ý viết ra: listener gọi một service, service gọi service khác, mắt cuối publish lại chính kiểu đó. Điều kiện dừng là trách nhiệm của call site — thường là huỷ đăng ký của chính mình, hoặc một cờ trạng thái, trước khi publish lồng.
biếtException không chặn được listener sauMuốn chặn thì dùng cờ trong payload hoặc một event khác.
biếtThứ tự đăng ký là bảo đảm duy nhất về thứ tựHai listener mà kết quả phụ thuộc thứ tự giữa chúng là thiết kế dễ vỡ: thứ tự đó theo Awake/OnEnable, tức thứ tự component trong scene.
biếtCần listener mới xử lý ngay event đang chạythì gọi thẳng nó một lần; bus chỉ đưa nó vào lượt sau.
biếtĐăng ký trùng so theo cặp object chủ + methodĐừng Subscribe lại để "refresh" đăng ký — không có tác dụng gì ngoài một dòng log. Hai lambda viết giống nhau không trùng: chạy hai lần.
biếtDọn danh sách chỉ xảy ra trong PublishBus hiếm bắn event mà call site Subscribe/Dispose liên tục thì danh sách nội bộ phình dần; một lần Publish là dọn sạch. Event không bao giờ bắn nữa thì ô chết nằm lại.
biếtKhông có Clear()Domain reload tự reset static mỗi lần vào Play Mode. Tick Disable Domain Reload thì listener static và lambda sống sót qua các lần chạy.
biếtNgân sách ~10–50 dispatch/giâyUI và luồng game, không phải hot path.
